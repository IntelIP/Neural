# Durable offline paper jobs

`neural.paper_worker` wraps the recorded-book simulator in a local SQLite queue.
Use a private directory on a local disk. No cloud, credentials or venue calls.

```sh
python -m neural.paper_worker --database /private/path/paper.sqlite3 submit \
  --strategy examples/strategy-price-rule.json --recording /path/to/books.jsonl \
  --cash 100 --fee-per-contract 0.01
python -m neural.paper_worker --database /private/path/paper.sqlite3 run-next
python -m neural.paper_worker --database /private/path/paper.sqlite3 inspect JOB_ID
```

Replace the placeholder ticker and paths. `submit` returns a queued job and ID;
`run-next` processes one queued job or returns JSON `null`; `inspect` reads its
persisted status/result/error. A processed invalid recording returns `failed`
with no result; command/input/storage errors exit nonzero. Callers must inspect
the status, not just the CLI exit code.

SDK: `PaperJobs(database).submit(spec, recording, initial_cash="100",
fee_per_contract="0.01")`, `.run_next()` and `.inspect(job_id)`.

## Persistence contract

- Recording bytes, canonical strategy and model assumptions are stored together.
  Identical bytes/configuration produce the same job ID, even after completion.
  Decimal spelling differences normalize. Byte-different recordings are different
  jobs even when semantically equivalent. Changing an external file cannot alter
  an already submitted job.
- SQLite uses FULL synchronous commits and a transaction across selection,
  simulation and result storage. Concurrent workers serialize. Crash before commit
  leaves the job queued; restart recomputes it. Crash after commit leaves the
  terminal result available. There is one committed result, **not exactly-once
  computation**. No incremental checkpoints or live-order recovery.
- Deterministic invalid input becomes terminal `failed`; operating-system/storage
  errors roll back and propagate so the job remains queued. There is no automatic
  retry loop. Fix input and submit a new job after a deterministic failure.
- One database writer at a time, five-second lock timeout, 32 MiB per recording
  and at most 10,000 events. SDK order-age limit is 1–86,400 seconds; default 30.
  Submission and inspection can report database-busy during processing. This is
  a bounded single-host runner, not a hosted scheduler or multi-tenant service.
- Queue has no automatic retention policy or total-disk quota. Operator owns
  disk capacity, directory permissions and SQLite-safe backups. Do not use network
  filesystems, share the database with untrusted writers, or delete active journals.
  Temporary recording copies are normally deleted; forced process death may leave
  an OS temporary directory. Input hashes detect corruption, not malicious tampering.

All recorded-paper execution assumptions still apply: caller-supplied fee,
single buy/exit cycle, no settlement or freshness certification. Model identity
is part of each job; incompatible future models must fail rather than silently
reinterpret queued work. No hosted worker or Vaticor UI is deployed here.

The current model is `neural-paper/2` (`neural.paper.PAPER_MODEL`). The model
participates in the job ID, so resubmitting model-1 inputs under model 2 creates
a new job instead of returning an old result. Completed model-1 jobs remain
available through `inspect`. Queued model-1 jobs fail explicitly as unsupported;
submit the original strategy, recording and assumptions again to run model 2.
Old results are not silently recalculated or relabeled with the new model.

## Read-only experiment queries

The experimental `neural.paper_query.PaperJournal` API lets consumers use saved
experiments without reading Neural's tables or starting a worker:

```python
from neural.paper_query import PaperJournal

journal = PaperJournal("/private/path/paper.sqlite3")
page = journal.history(offset=0, limit=25)  # jobs, has_more; no result traces
if page["jobs"]:
    job_id = page["jobs"][0]["id"]
    saved = journal.inspect(job_id)  # id, status, error, config, result
    original_bytes = journal.recording(job_id)
```

Queries open an existing journal in SQLite read-only mode, without acquiring a
writer reservation, creating a queue, migrating its schema or running simulation.
Missing files raise `FileNotFoundError`; unknown jobs, invalid stored data and
unsupported journal versions raise `ValueError`. History orders by insertion,
newest first; offset is 0–100,000 and page size is 1–100. No timestamps are invented.
Reading can still report database-busy if SQLite holds an exclusive lock.

`recording(job_id)` verifies the stored configuration/job identity and the original
recording's size and digest before returning its exact bytes. Inspection preserves
historical results as recorded; it does not recalculate them or certify their
correctness. The caller selects the runtime archive and verifies its wheel and
environment identity. This API does not authenticate users or grant data rights.

`compare(first_id, second_id)` returns two completed jobs with derived
`total_fees`, `fill_count` and `rejection_count` in their result objects. Recording,
model, market/outcome, cash, fees and simulation limits must match; strategy
thresholds and risk limits may differ. Summaries use exact decimals and never
write back to the journal. Missing historical traces reject comparison explicitly.

`compare_markets(first_id, second_id)` separately returns `ids`, supplied `markets`
and a sports `comparison`. It can inspect cross-venue contract metadata, but never
compares performance or execution costs. Missing sports metadata rejects the
request. Keep the existing `PaperJobs` write/worker API for submission and processing;
its methods and the journal format are unchanged.
